# REA-LAB — GoldJewel, a working iOS/iPadOS slice of MatrixGold

This repository contains two things that are easy to confuse, so this file
separates them:

1. **An evidence lab** that reverse-engineers Gemvision MatrixGold 3.1
   (build `3.1.22284.1001`, .NET Framework 4.8, WPF, Rhino 7 plugin) without
   executing vendor code.
2. **GoldJewel**, a universal iPhone/iPad app built from that evidence: a small,
   document-based parametric jewelry editor that renders and edits one family
   of ring-head geometry, carries the real ring-size tables, and exposes the
   product's v1 service contract as an operation catalogue.

GoldJewel is **not** MatrixGold, is **not** a Rhino client, and is **not** a
complete jewelry CAD program. It is a deliberately scoped, simulator-verified
port of the parts the evidence can currently support, with everything it does
not implement labelled as an entry point rather than faked. The rest of this
file states exactly what runs, what is reconstructed, and what has never been
measured.

```text
App:        GoldJewel 0.1.0 (build 1)
Platform:   iOS / iPadOS 17.0+, universal (TARGETED_DEVICE_FAMILY 1,2), Swift 6
UI:         SwiftUI, generated by XcodeGen; no third-party dependencies
Renderer:   CPU Canvas (painter's algorithm); no Metal, RealityKit or SceneKit
Documents:  JSON in Application Support, autosaved
Geometry:   round solitaire head — basket, 4/6/8 prongs, dome caps, gallery
            rail, optional bezel, optional halo
Sizing:     22 ring regions, 7,005 sizes executed from the shipped DLL
Operations: 88 v1 catalogue entries — 12 wired, 76 explicit entry points
Tests:      35 XCTest cases in JewelryKit; XCUITest runtime gate on iPhone and iPad
Verified:   Linux, macOS and both pinned simulators; never a physical device
```

## 1. What the app actually is

GoldJewel is a small document app with three surfaces. There is no account, network call,
telemetry, cloud sync, import wizard or renderer setting.

### Project list

A `NavigationSplitView` list of saved designs with create, select and
swipe-to-delete. It becomes a stacked navigation on iPhone and a split view
with a sidebar on iPad. Each row shows the design name, gem diameter and prong
count. A footer shows the catalogue totals (`88 v1 operations · 12 wired`) and
the last autosave time. Projects are real documents: they survive termination
and relaunch.

### Editor

A single scroll view with an orbitable head preview and these controls:

| Group | Controls |
|---|---|
| Project | Editable name, committed on submit or focus loss, and a last-saved timestamp |
| Head | 4 / 6 / 8 prongs; gem diameter 4–12 mm; head height; prong height; side angles X and Y; top angle; base angle; base position |
| Domed prongs | Toggle plus dome height, setting distance and setting angle |
| Gem and ring | Metal name (6 options); ring region (all 22); real size list for that region; inner diameter and circumference readout |
| Gallery rail | Toggle plus height along rail, width, thickness and gem offset |
| Bezel | Toggle plus seat height, seat length and seat angle |
| Halo / cluster | Toggle plus melee diameter, spacing, rail offset, rail height, seat rotation and even stone count |
| Evidence | The number of IL-traced literals and the provenance grade of every visible family |

The **metal picker is document metadata only**: it is saved and reloaded, but it
does not shade or weight the preview yet. The **ring size** is likewise metadata
and a lookup, not a rendered band — the app has no shank geometry.

### Preview

`HeadPreviewView` projects the generated triangle mesh itself: a small software
renderer with flat shading, a fixed light, depth-sorted faces and drag-to-orbit.
It deliberately uses no 3D framework, so the recovered geometry can later be
moved to Metal without changing the builder API. The view's accessibility value
reports the prong count, the number of graded families and the triangle count.

| Configuration | Triangles |
|---|---:|
| Basket plus 4 prongs, no domes or rail | 9,984 |
| Default head: basket, 4 prongs, dome caps, gallery rail | **18,688** |
| Every family enabled: adds bezel and a 17-stone halo | **21,144** |
| Per prong | 2,304 |
| Per dome | 1,920 |
| Gallery rail | 1,024 |
| Bezel | 1,024 |
| Halo band + proxy melee | 1,432 |

### Operations sheet

The sheet lists **all 88 v1 operations** from
[`08-reports/capability-matrix.csv`](08-reports/capability-matrix.csv), grouped
by cluster, with search and a detail view. Twelve are wired to real behaviour;
the other 76 say *Entry point only* and deliberately expose **no Run control**.
The twelve wired operations are:

`DeleteBuilder`, `ExecuteBuilderCommand`, `GetActiveBuilderId`,
`GetActiveDocPath`, `GetAllBuilderGuids`, `GetCurrentFileIsModified`,
`GetDefaultRingSizeRegionAbrv`, `GetRingSizeRegionAbrvs`,
`GetRingSizesFromRegionAbrv`, `ReadJsonFromDocument`,
`SetCurrentFileAsNoModified`, `WriteJsonToDocument`.

`ResizeRing` and `SetDefaultRingSizeRegionAbrv` are **not** wired: the shell has
no shank geometry and no app-level default-region setting. They are present as
entry points, are asserted as such by the runtime gate, and cannot be run into
reported work. The catalogue is generated by
[`Tools/operation_catalog.py`](Tools/operation_catalog.py); `--check` fails CI if
it drifts from the capability matrix or if a newly wired operation has no
`ProjectStore` case.

### Documents and persistence

`JewelryProject` stores the gem, prong count, every head angle, metal, ring
region and size, rail settings, dome settings and the optional bezel/halo
settings. The list is written as pretty-printed, key-sorted JSON with ISO-8601
dates to `Application Support/GoldJewel/projects.json` using an atomic write.
Saves are coalesced by 450 ms and flushed when the app leaves the foreground, so
typing and slider drags do not rebuild the split view on every event. Older
documents decode with the dome on and bezel/halo off. The launch argument
`-reset-projects` exists solely so the runtime test starts from a clean
document; normal use cannot trigger it.

### What the app deliberately does not do

* No ring band/shank in the interface, no cutters, booleans or `Sweep1` surfaces.
* No `.mgm` import UI and no PBR shading; `MGMaterial` is a library decoder only.
* No gem-size numeric tables, only the ring-size tables and the catalogue schema.
* No full 254-operation service surface; only the 88 operations the matrix marks
  as v1, and only 12 of those are implemented.
* No signing, archive, TestFlight, CloudKit, localization, authentication or
  licensing. Those are out of scope by design.
* No physical-device or hardware-renderer verification. See §3.

## 2. The geometry, and how much to trust each part

The app builds a round solitaire head from the recovered `CSHeadShape` formulas
and four supporting families. Every visible part carries an explicit grade:

| Part | Grade | What that means |
|---|---|---|
| Basket | **recovered** | Four lofted outlines from IL; 128 girdle points and the three scale transforms are checked against golden vectors |
| Prongs | **inferred** | Section dimensions are fixture values because the authoring family is not in corpus v1; rails and the two-section loft are reconstructed |
| Dome caps | **reconstructed** | Captured `BlendCurve` fractions and apex rules; the meridian start tangent is radial, not the vendor's surface split |
| Gallery rail | **inferred** | Height rule and offsets are recovered; the band is rectangular and the ellipse offset is approximated |
| Bezel | **reconstructed** | `BezelProfile` seat polyline is captured; the collar wall and radial normal are reconstructed |
| Halo seats | **recovered** | `PlaceGems` count, phase, wrap, even adjustment and sort are captured |
| Halo band | **reconstructed** | Seat path from the offset girdle; the authored profile is not reproduced |
| Halo melee | **inferred** | Octagonal proxy crowns at measured seat positions, not `CSGemInstance` faceting |

The package resource
[`head-geometry-provenance.json`](07-ios-handoff/JewelryKit/Sources/JewelryKit/Resources/head-geometry-provenance.json)
holds **19 IL literals** and **13 claims**. Swift tests require every literal to
be traceable to a method and IL offset, every reconstructed claim to name an
algorithm, every inferred claim to give a rationale, and every visible part to
have a grade.

This is a **reconstruction**, not a reproduction, of Rhino solids. The vendor
assembly has never been executed (limitation #4): the constants and control
flow are exact, but no builder output from MatrixGold has ever been measured.
The Swift implementation is verified against the decompiled algorithm and its
own golden vectors, not against the vendor binary.

### Ring sizing

The `RingSizing` module is the most exact part of the port:

* **22 regions**, **7,005 sizes** executed from the real `CSRingSizes.dll` and
  embedded byte-identically as a package resource.
* Closed-form diameter/index formulas reproduced with the vendor's
  `Math.Round(value, digits)` behaviour, i.e. mid-point-to-even, not
  away-from-zero.
* **565 / 565** closed-form parity checks and **7,005 / 7,005** structural
  validations (index sequence, radius derivation, plausible diameter).

### Materials and domain

`MGMaterial` decodes the 55-field `.mgm` material model with the 20
`MaterialMapData` keys, and `JewelryDomain` supplies gem, metal and setting
types. The Windows validator checks those keys and every enum raw value against
**257 / 257 real `.mgm` files**. Three fixtures ship with the tests: two real
files with embedded previews stripped, and one synthetic sample. The app itself
does not read `.mgm` files.

### ParametricKit

The package also declares a kernel-independent `GeometryPlan` vocabulary
(revolve, sweep, loft, booleans, fillet, offset, polar array, mirror, mesh) and
a band builder. It is a seam for a future OCCT/Rhino Compute/Metal backend; the
app does not use it to render a shank.

## 3. How the software is verified

### CI gates

| Workflow | Runs on | What it proves |
|---|---|---|
| [`linux`](.github/workflows/linux.yml) | every push to `main`, PRs, manual | Validator (materials, ring vectors, regions), M2 corpus/ledger hashes, corpus v2 hashes, head/dome/bezel/halo golden vectors and IL provenance, operation catalog versus matrix, then `swift build` + `swift test` on `swift:6.0` with a guard that `JewelryKit` stays Foundation-only |
| [`macos`](.github/workflows/macos.yml) | pushes touching `07-ios-handoff/**`, manual | `swift test` on macOS 15 with the full XCTest suite |
| [`ios-simulator`](.github/workflows/ios-simulator.yml) | pushes touching `07-ios-handoff/**`, manual | Budget check, XcodeGen, a fresh simulator build, then the XCUITest runtime gate on a pinned iPhone and iPad, with screenshots and `.xcresult` artifacts |

The Linux workflow is intentionally two jobs: `artefacts` re-verifies the
committed evidence, `package` proves the package builds and tests on a non-Apple
toolchain.

### The runtime gate

[`07-ios-handoff/App/run_runtime_gate.py`](07-ios-handoff/App/run_runtime_gate.py)
builds the test bundle once, requires these exact simulators, and runs the same
test on each:

* **iPhone SE (3rd generation)**, iOS 18.6
* **iPad mini (A17 Pro)**, iOS 18.6

A missing pin is a loud failure, not a silent fallback to whatever runtime the
runner image has. Each device gets up to two attempts, a 5 s delay and a 60 s
shutdown between them; a wedged run is killed, not skipped. On success every
attachment is exported under a readable name to
`build/runtime-evidence/{iphone,ipad}/` (14 PNGs per device) with a
`manifest.json` and `summary.json`; the run fails if a passing test produced no
screenshots.

The XCUITest drives the real UI and asserts:

1. Launch into the foreground, project creation, and the editor/preview.
2. The operations sheet's exact totals (`88 v1 operations · 12 wired · 76 entry
   points`), all twelve wired rows as `wired`, `ResizeRing` and
   `SetDefaultRingSizeRegionAbrv` as `entry-point`, both pending details saying
   *Entry point only* with no Run control, and a real run of
   `GetActiveBuilderId` producing a result.
3. A non-blank render: a 48×48 downsample must contain more than **2 %**
   gold-coloured pixels.
4. Name editing through the real keyboard.
5. All four geometry families: rail off, domes off, bezel on, halo on — each
   switch's value flips, the preview's accessibility value changes, and the
   48×48 luminance differs from the previous capture by at least **0.005**.
6. The gem-diameter slider moving 6.5 → 9.8 mm, with a rebuild and at least
   **0.01** pixel difference.
7. Terminate and relaunch without the reset argument: the edited project, name,
   pixel content and family state must all survive.

passed on attempt 1** with no device retry and no scroll failure:

### What the gate cannot prove

* Physical devices, signing, archives, TestFlight, Release builds.
* Metal/GPU behaviour, frame rate, battery, thermal state.
* Form factors beyond the two pinned devices: no notch/Dynamic Island, no 11"
  or 13" iPad, no landscape, Split View, Stage Manager or external display.
* Delete/reload flows, rotation, accessibility settings (VoiceOver, Dynamic
  Type), dark/light switching, locales or performance.
* Vendor geometry parity. No MatrixGold solid has ever been measured.

## 4. Repository map

The repository is intentionally lean: **112 tracked files**. Large or
regenerable artifacts are git-ignored and absent from a fresh clone.

| Path | Tracked? | Contents |
|---|---|---|
| `07-ios-handoff/App/` | yes | XcodeGen spec, SwiftUI sources, XCUITest, runtime gate |
| `07-ios-handoff/JewelryKit/` | yes | Swift package: ring sizing, material I/O, domain, parametric seam, head geometry, tests and fixtures |
| `08-reports/` | yes | Index, coverage, limitations, triage ledger, capability matrix, M2–M6 reports, C: cleanup |
| `06-dossiers/` | yes | Eight implementation dossiers (shell, persistence, presentation, kernel, parametric construction, gems/materials, ring sizing, content/localization) |
| `05-evidence/` | yes | IL corpus v1/v2 with hashed manifests, golden ring-size and head-geometry vectors, REA evidence indexes and budget patch |
| `04-index/` | partly | Ledger builder, handoff validator, XAML binding inventory and coverage summary; `symbols.sqlite` and the raw scan cache are generated |
| `00-control/` | yes | PowerShell stages for environment, mirror, manifest, decompile, CIL, BAML, REA, clean-up; helper library |
| `Tools/` | yes | Corpus capture/verify, triage, capability matrix, operation catalogue, geometry vectors, Oracle capture harness |
| `.github/workflows/` | yes | The three CI gates above |
| `01-target/` | **no** | Frozen read-only MatrixGold mirror and SHA-256 manifest; licensed binaries never committed |
| `02-toolchain/` | **no** | Node, REA, ILSpy, SymbolScan, BamlTool and the RingVectors harness |

Why the split: the mirror alone is 1.8 GiB of licensed binaries, and the
decompilation adds roughly 170 MB of derived source; the tracked evidence is the
facts, hashes, vectors and reports that make the claims checkable. A clone can
verify everything that does not require the vendor install or a Mac.

## 5. Reproduce

### Evidence checks (Windows, Linux or macOS)

```bash
python 04-index/validate_handoff.py            # expect 0 failures
python Tools/m2.py --check                     # corpus v1 hashes, 50,134-method triage, 254-op matrix
python Tools/build_corpus_v2.py --check        # corpus v2 hashes and counts
python Tools/head_geometry_vectors.py --check  # golden vectors and IL provenance
python Tools/operation_catalog.py --check      # 88 operations, 12 wired, no drift
```

The last four are exactly what the Linux `artefacts` job runs. The full
lab pipeline (mirror → manifest → index → decompile → CIL → ledger → BAML →
REA → vectors) needs the licensed install at its original path, Windows,
PowerShell, .NET and ILSpy; the stage map with every entry point and output is
in [`08-reports/00-INDEX.md`](08-reports/00-INDEX.md).

### The app and its runtime gate (macOS with Xcode 16)

```bash
cd 07-ios-handoff/App
brew install xcodegen
xcodegen generate
python3 run_runtime_gate.py --check-budget
python3 run_runtime_gate.py
```

The gate builds for the simulator, installs on the two pinned devices, runs the
UI test on each, retries a device once, and writes `build/runtime-evidence/`.
There is no Swift toolchain on the Windows machine this lab was built on; local
Swift compile and runtime evidence therefore come only from CI, which is why the
gate is the primary artifact.

## 8. The limitations that matter

1. **No vendor execution.** `CSBlocks.mgp` is mixed-mode and fails to load
   outside Rhino (`ERROR_DLL_INIT_FAILED`). Geometry is `inferred-from-IL`; the
   runtime oracle (Frida hook or exported golden solids) is still outstanding.
2. **Simulator-only proof.** No signed build, physical device, Metal renderer,
   Release configuration or performance measurement exists.
3. **Two form factors.** iPhone SE and iPad mini, portrait, iOS 18.6 only.
4. **Twelve of 88 v1 operations are wired; 76 are entry points.** The wider
   service contract has 254 operations, of which the 88 are the v1 subset. The
   app reports what is pending rather than pretending.
5. **Only the head is modelled.** No shank/band UI, cutters, booleans or full
   `Sweep1` surfaces. Domes, bezels and halo bands are reconstructions.
6. **Numeric gem-size tables and localization strings are documented but not
   extracted.**
7. **No PDBs and SmartAssembly name mangling.** Citations use types, methods, IL
   offsets and file paths; 55.2 % of `MatrixGold.exe` type names are mangled.
8. **The D: volume is a USB SSD and has dropped out during this work.** Every
   long write was re-read; if a drive disconnects, re-run the validator.
9. **Nothing in the app depends on the network.** There is no service to be
   down; conversely, there is no sync, sharing or cloud backup.

## 9. Content, licensing and repository boundary

No vendor binary, licensed asset or full decompiled tree is committed. The
tracked corpus contains derived facts, IL text, hashes and vectors, plus three
test `.mgm` fixtures: two real files with embedded previews stripped and one
synthetic sample, used only to test the decoder. Licensing, accounts and
entitlement code are deliberately out of scope. The repository is public
(`github.com/shahrdazri-ctrl/goldjewel`) so CI can use hosted macOS runners;
nothing in the build depends on that visibility. The remaining risk register,
with mitigations, is [`08-reports/limitations.md`](08-reports/limitations.md).
